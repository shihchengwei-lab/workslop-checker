# AI 文件驗收 / Workslop 檢查

## 這 skill 在做什麼

判斷一份文件能不能被人接手、使用、送出、決策。

**重點不是抓 AI、不是評美感**。重點是：這份文件會不會把修正成本丟給接手者？

定位句：
> 這不是用來抓 AI，而是用來防止 AI 產物把修正成本丟給接手者。

## 不適用的場景

- 對話品質檢查（每輪回答的好壞）
- 程式碼 review
- 給人讀的非交付內容（聊天紀錄、便條、隨筆）

遇到上述場景請拒絕觸發，告訴使用者這 skill 只驗收成品文件。

## 流程

1. **先跑紅燈**（任一命中 → Red，直接退回，不要進驗收）
2. **再跑驗收**（八類，逐項 Pass / Fix / Fail）
3. **看 URL 驗證**：文件含外部連結時
   - 你有 web fetch / browse 工具 → 抓 HTTP status，列出失效連結
   - 沒有 → 把所有 URL 列成清單，標「需人工驗證」，不要假裝檢查過
4. **下結論**：Green / Yellow / Red + 必修項目 + 修正指令

## 文件類型判斷

跑紅燈之前先判斷文件類型，紅燈條件對不同類型適用度不同：

- **Action 文件**：交付物、SOP、決策 memo、提案、執行計畫、PRD。完整套用所有紅燈
- **方法論／規範／教學**：清單、指南、規則書、教材、checklist、framework。豁免「責任不清」（方法論本身沒 owner 是正常的）；「接手成本過高」改用「方法本身可不可執行」判斷，不是「誰執行」判斷；「事實無來源」對借用的業界既有術語放寬，對核心主張的支撐仍嚴格
- **報告／分析**：研究、市場分析、調研。「事實無來源」「引用疑似偽造」用最嚴格標準
- **對外溝通**：客戶信、公告、行銷文案。「外部文件未揭露 AI 使用」「風險被淡化」用最嚴格標準

### 優先規則：文件自我宣告

跑前先看文件是否自我宣告為範本／模板／教學樣本。若有以下任一訊號，**強制歸「方法論／規範／教學」類**，優先級高於下面的 fallback 預設：

- 標題或內文含「範本」「template」「樣本」「sample」「填寫指引」「示範」「pattern」
- 多處註腳「以下為範例」「僅供參考」「業者應依實際作業完備」「請依需求調整」
- 大量結構性佔位符（○○、XXX、YYYY/MM/DD、{{...}}）——這些是設計特性、不是缺漏

這條規則防止把「範本」誤判為「半成品 SOP」。範本要驗範本完整性（結構閉環、附件齊全、術語有定義、流程可照填），**不要苛責它「沒填好」**。

### 官方範本特別規則

若文件是政府機關、主管機關、學校、醫院、公司總部、法遵單位等權責單位正式發布，且用途是提供業者、單位或承辦人套用的 SOP 範本、指引範本、表單範本，應**優先視為「已發布的範本文件」而不是「待交付的實際 SOP」**。

**明確豁免（不扣分）**：
- 含有佔位符
- 要求業者依實際情況調整
- 沒有列單一 owner
- 沒有填入業者內部日期與人名

這些是範本特性、不是缺漏。

**來源處理**：對官方範本，來源可信度視為 Pass；不要要求每一條常規作業文字都另附來源。

**高風險領域**（法律、醫療、食品安全、財務、資安、個資）：「官方範本」不因為沒有個別業者的人工覆核標示而自動 Red 或 Yellow；實際落地前需要內部負責人確認，**只能列為使用提醒，不能當作範本本身的扣分**。

**官方範本可以 Green 的條件**（需全部符合）：
- 文件明確是範本或指引
- 發布者是相關權責單位或可信組織
- 目標使用者與用途可辨識
- 結構足以讓使用者照填或照做
- 佔位符是有意設計
- 沒有內部矛盾、偽造引用、敏感資料外洩、核心步驟缺失、錯誤風險淡化

若全部符合，即使仍需業者填寫實際資訊，也應給 Green，並在「能不能用」說：「可作為範本使用；實際採用前需依自身情況填寫與確認」。

### Fallback

判不出來、且無範本自我宣告訊號時：假設是 Action 文件、用最嚴格標準。文件類型在驗收輸出開頭明說，讓使用者能複查判斷。

## 文件成熟度判斷

文件處於不同成熟度，驗收嚴格度應對應調整。**草稿模式需明確觸發**——不從弱訊號自動推斷，避免誤把已交付文件當草稿放行。

### 草稿模式觸發條件（需滿足任一強訊號）

1. **使用者明確指定**：觸發詞含「驗收草稿」「草稿驗收」「draft check」「以草稿驗收」「這是草稿」「以 draft 狀態」「跑草稿驗收」等明確措辭
2. **文件強訊號**（任一）：
   - 標題明確含 **DRAFT / 草稿 / 初稿**（注意：「初版」「v0」「WIP」不算強訊號）
   - 第一段或頁首明確宣告「本文件尚未定稿」「請勿引用」「For Review Only」「Working Draft」「Pre-decisional」
   - 全文大量明顯未完成標記：多處 TODO、[待補]、空白章節、佔位符未填超過 30% 字數

### 弱訊號處理（不自動降草稿、但要提示）

弱訊號包含：v0、v0.x 版次、WIP、少量 TODO、開發中專案文件、README 等。

處理方式：**仍按「準交付」嚴格度驗收**，但在輸出開頭加提示：「文件有 [具體弱訊號] 但未明確標 DRAFT。我用準交付標準。若實為草稿，請明說『以草稿驗收』再跑一次。」

### 三階段嚴格度對應

| 階段 | 觸發條件 | 可修紅燈 | 驗收 E（可執行）| 驗收 F（接手）|
|---|---|---|---|---|
| 草稿 | 強訊號或使用者明說 | 「責任不清」「缺少關鍵限制」放寬 | 放寬：看「方向是否清楚」非「步驟是否完整」 | 放寬：尚未到接手點 |
| 準交付 | 預設、或有弱訊號 | 標準 | 標準 | 標準 |
| 已交付 | 正式版次 v1.0+、生效日期、簽核痕跡、明確公開發布 | 標準 | 最嚴格 | 最嚴格 |

判斷不出來、又無弱訊號：預設「準交付」標準嚴格度。**不靠模糊訊號降標準、不預設草稿**。

**硬紅燈不因成熟度放寬**：敏感資料外洩、偽造引用、高風險領域未審、核心事實不可查、目的完全不明、接手成本災難級——這些與成熟度無關，草稿也不能踩。

草稿狀態的 Green 意義：「以草稿狀態而言可繼續完善、方向正確」，**不等於可立即交付**。輸出時請明說此區別，避免使用者誤把「草稿 Green」當「可發布 Green」用。

## 第一層：紅燈

紅燈分兩級：

- **硬紅燈**命中任一 → Red，直接退回，不進驗收
- **可修紅燈**命中 → 不退回，但升級為驗收 Fix、計入結論

### 硬紅燈（命中任一 → Red）

- **目的完全不明**：無法判斷文件要讓讀者做什麼、要解決什麼問題
- **引用疑似偽造**：引用、連結、論文、案例無法查證或明顯捏造
- **核心事實不可查**：文件的主要結論依賴的事實沒來源、無法驗證
- **敏感資料外洩**：API key、token、客戶資料、帳號、密碼等出現在文件內
- **高風險領域未人工覆核**：涉及法律／醫療／財務／資安／個資／合約，但未標記需人工確認
- **接手成本災難級**：結論依賴外部知識，文件內未提供也未指向來源或材料，讀者必須從零重做

### 可修紅燈（命中 → 升 Fix、不退回）

- **缺來源（非核心事實）**：數字／日期／人名沒附來源，但不影響主要結論
- **事實與建議混在一起**：段落內事實與建議混雜，讀者較難分辨
- **缺少關鍵限制**：沒寫適用範圍、例外、前提（依文件類型嚴格度調整）
- **內容太泛**：是通用方法論／模板，但沒留可填入具體情境的位置
- **責任不清**：Action 文件無 owner／時間／完成標準（方法論／規範類豁免）
- **外部 AI 未揭露**：對外發送但未經人工審閱（依組織政策；無政策時建議標）

紅燈判斷原則：**不是問「寫得好不好」，是問「會不會害接手者承擔隱藏成本」**。硬紅燈是「不能交付」的底線；可修紅燈是「交付前要先處理」的待辦。

## 第二層：驗收（紅燈過了才跑，逐項 Pass / Fix / Fail）

### A. 任務符合度
- 文件目的明確（第一段就講清楚解決什麼問題）
- 沒偷換題目（沒把「分析」寫成「宣傳」、「決策 memo」寫成「知識文章」）
- 使用場景明確（誰會在什麼情境用）

### B. 事實與來源
- 關鍵事實可追溯（數字／日期／專有名詞／案例有來源或附件）
- 來源層級清楚（區分一手、二手、個人觀察、推測）
- 沒過期資料（時效性資訊有日期）
- 沒把 AI 輸出當來源

### C. 事實／推測／評價分離
- 已確認事實獨立呈現
- 推測有明確標記（「我推測」「可能」「尚無法確認」）
- 評價有明確標記
- 結論沒超出材料
- 不用語氣掩蓋不確定性（不用「顯然」「必然」「毫無疑問」包裝推測）

### D. 完整性
- 有涵蓋必要背景
- 有列出缺口（明確寫目前不知道什麼）
- 有列出例外情境
- 有處理利害關係人

### E. 可執行性
- 有具體下一步（不是只提供觀點）
- 每個下一步有 owner
- 有時間或優先順序
- 有完成標準

### F. 接手成本
- 不需要原作者口頭補充就能理解
- 術語有定義（內部代號、縮寫、專有名詞）
- 脈絡不藏在聊天紀錄裡
- 有未解問題清單

### G. 語氣
- 沒有 AI 常見空話（提升效率／賦能／創造價值／最佳實踐／一站式／無縫／全方位）
- 沒有過度自信（不用漂亮語氣掩蓋缺口）
- 標題準確，不是行銷式

### H. 風險與邊界
- 高風險內容有標記人工覆核（法律、財務、醫療、資安、個資、合約）
- 沒敏感資料外洩（客戶資料、內部資料、API key、token、帳號）
- 有決策邊界（本文可支持什麼、不能支持什麼）

## 第三層：結論

| 結果 | 條件 | 意義 |
|---|---|---|
| **Green** | 硬紅燈 0、可修紅燈 0；驗收 80% 以上 Pass、無 Fail | 可直接交付，僅需小幅修正 |
| **Yellow** | 硬紅燈 0；有可修紅燈／Fix／Fail | 可修後使用 |
| **Red** | 硬紅燈命中任一 | 退回重做 |

## 寫作原則

- **不評分美感**：不寫「文字流暢」「結構清晰」這類主觀判斷。問「讀者第一段能不能知道用途」這種可驗證的問題
- **修正指令要可執行**：不寫「請改進事實性」。寫「請把所有含數字／日期／公司名的句子列成表格，逐一補來源；無法補的標記為『未確認』或刪除」
- **不假裝**：URL 沒驗證就明說「未驗證」，不要寫「應該都能打開」
- **不為了 Green 而 Green**：紅燈命中就 Red，不要因為「整體看起來不錯」就降紅燈
- **不挑 AI vs 人寫**：不問「這是不是 AI 寫的」，問「這份文件是否把修正成本丟給接手者」
- **材料前結論後**：先列觀察到的具體問題，再下 Green/Yellow/Red，不要倒過來
