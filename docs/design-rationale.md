# 設計理由

這份文件解釋 `verify-doc / Workslop Checker` 的關鍵設計決策——為什麼這樣寫、不那樣寫。給想 fork、客製、或想理解工具邊界的人看。

## 為什麼紅燈分硬／可修兩級？

最早版本只有「紅燈」一級——任一命中就退回。實測發現 false positive 太多：

- 短 memo 把事實和建議寫在同一段 → 不該整份退回，只是要重組
- 文件沒寫「適用範圍、例外、前提」 → 對方法論文件可能 OK、對 Action 文件才嚴重
- 「外部 AI 未揭露」 → 看組織政策，不是普世規則

**解法**：分兩級

- **硬紅燈**：命中任一就 Red、不該交付。例如偽造引用、敏感資料外洩、目的完全不明
- **可修紅燈**：命中不退回但升 Fix，計入結論。例如缺來源、混事實建議、責任不清

這降低了「好文件被誤判 Red」的 false positive，但保住對嚴重問題的硬底線。

## 為什麼有「文件類型判斷」？

同樣的紅燈條件套到不同文件類型會誤判：

| 紅燈條件 | Action 文件 | 方法論／規範 | 報告／分析 | 對外溝通 |
|---|---|---|---|---|
| 責任不清（沒 owner）| 致命 | **豁免**（方法論本來沒 owner）| 不適用 | 不適用 |
| 事實無來源 | 嚴重 | 對借用業界術語放寬 | **最嚴格** | 嚴格 |
| 未揭露 AI | 通常不適用 | 不適用 | 看狀況 | **最嚴格** |
| 風險被淡化 | 嚴重 | 嚴重 | 嚴重 | **最嚴格** |

「方法論／規範類」不該因「沒 owner」整份退回——這類文件設計上就沒指定 owner。

## 為什麼有「官方範本特別規則」？

「方法論／規範」豁免「責任不清」「業界術語」後，實測時對「官方範本」（政府／公協會發布的 SOP 範本）仍會誤判 Yellow——因為佔位符（○○、XXX、YYYY/MM/DD）被當成「缺漏」。

**解法**：加一層更專門的規則。「官方範本」**明確豁免**：

- 含佔位符
- 要求業者依實際情況調整
- 沒列單一 owner
- 沒填入業者內部日期與人名

這些是**範本性質**、不是缺漏。把範本當「半成品 SOP」苛責是 false positive。

但豁免不是無條件 Green。Green 仍要符合：結構完整、可照填、無內部矛盾、無偽造引用、無敏感資料外洩、核心步驟不缺、風險未淡化。

## 為什麼有「文件成熟度」？

草稿（v0、未定稿）和已交付版用同一標準也誤判：

- 草稿被苛責「沒 owner、沒填好限制、下一步不完整」——但草稿本來允許這些未定
- 已交付版被放過該嚴格抓的問題

但**自動判斷「這是草稿」太鬆**會放行已交付文件。所以採：

- **強訊號才走草稿**：使用者明說「驗收草稿」、標題明含 DRAFT/草稿/初稿、明確未定稿宣告、TODO 超過三成
- **弱訊號（v0、WIP）不直接降標**：走準交付，但開頭提示使用者「若實為草稿請明說再跑」

**硬紅燈仍不放寬**，草稿也不能踩。

## 為什麼八類驗收（不是五類、不是十類）？

八類對應「接手成本」的不同面向：

| 類別 | 對應接手者會踩到的問題 |
|---|---|
| A. 任務符合度 | 文件根本沒回答原始問題、偷換題目 |
| B. 事實與來源 | 接手者要再花時間查證 |
| C. 事實／推測／評價分離 | 接手者把推測當事實做決策 |
| D. 完整性 | 接手者要回頭問「這背景怎麼來的」「有沒有遺漏」 |
| E. 可執行性 | 接手者不知道下一步、不知道誰負責 |
| F. 接手成本（其他面向）| 術語沒定義、未解問題沒列、要原作者口頭補充 |
| G. 語氣 | AI 空話矇蔽缺漏（「賦能」「最佳實踐」「一站式」）|
| H. 風險與邊界 | 接手者不知道高風險領域要人工覆核 |

壓成五類會丟失 B/C、D/F 的細節區分。維持八類精確。

對外 ChatGPT GPT 輸出時把驗收細節壓在「前三個問題」段——對外使用者要的是「可以用嗎、怎麼修」，不需要看完整評分表。內部 Claude skill 保留完整八類輸出供使用者複查。

## 為什麼不抓「這是 AI 寫的」？

`verify-doc` 不是 AI 偵測器（像 GPTZero）。

- AI 偵測器準確度不高、誤判率高
- 即使準確，「是 AI 寫的」這個資訊對「能不能用」沒幫助
- 人寫的文件也可能是 workslop；AI 寫的文件也可能很好
- 把焦點放在「接手者成本」更實用

## 對外 GPT vs 內部 Claude skill 為什麼不同？

| | 對外 ChatGPT GPT（5 段輸出）| 內部 Claude skill（完整版）|
|---|---|---|
| 對象 | 非工程使用者、想快速決策 | 開發者、想完整評鑑 |
| 八類驗收細節 | 壓進「前三個問題」 | 完整顯示 A-H Pass/Fix/Fail |
| URL 驗證段 | 整合進主流程 | 獨立列出 |
| 必修／可選／不可用／人工覆核 | 合成「怎麼修」 | 分四段 |

兩個版本各自演化、不要硬同步。

## 這些設計決策怎麼來的？

每條都從實測 false positive / false negative 案例往回推：

- 紅燈分級 ← StockFeel 法說會分析、Output_check_list.md 兩份實測，舊版誤判 Red
- 官方範本特別規則 ← 政府 SOP 範本實測，先 Yellow、補規則後 Green
- 文件成熟度區分 ← Output_check_list.md（v0 草稿）vs 已發布範本，標準不同
- 「不抓 AI」哲學 ← 從一開始就排除這方向，避免變成第 N 個 GPTZero

設計過程紀錄在這個 repo 的 commit history 跟 issue（push 後）。
